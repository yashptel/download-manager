# OpenDM for Windows

WinUI 3 (Windows App SDK 1.8), unpackaged, on the same Rust core as the
macOS app. The core is reached through C# bindings generated by
[uniffi-bindgen-cs](https://github.com/NordSecurity/uniffi-bindgen-cs).

> **Status:** builds without warnings and runs on Windows 11 (x64). The arm64
> build has not been tried.

## Prerequisites

- Windows 10 1809 or later (Windows 11 recommended)
- Visual Studio 2022 Build Tools with **Desktop development with C++** (MSVC
  and the Windows SDK, needed by Rust)
- [.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0)
- [Rust](https://rustup.rs) with the MSVC toolchain
- Git and PowerShell

With winget: `winget install Microsoft.DotNet.SDK.10 Rustlang.Rustup`.

## Build

```powershell
scripts\build-windows.ps1              # x64 Release -> build\windows\OpenDM-x64\OpenDM.exe
scripts\build-windows.ps1 -Arch arm64
```

The script downloads the pinned aria2-next build and checks its SHA-256,
builds the Rust core (`opendm_core.dll`), installs the pinned C# bindings
generator into `build\tools` on first use, generates `OpenDM\Core\opendm_core.cs`,
copies the native files into `OpenDM\Native` and publishes the app. After one
run, `OpenDM\OpenDM.csproj` also opens and builds in Visual Studio.

Run against a scratch data folder during development:

```powershell
$env:OPENDM_DATA_DIR = "$env:TEMP\opendm-dev"
build\windows\OpenDM-x64\OpenDM.exe
```

A `settings.json` in that folder with `{ "download_dir": "C:\\scratch\\downloads" }`
keeps test downloads out of your Downloads folder.

## Test

```powershell
scripts\fetch-engine.ps1
cargo test -p opendm-core
```

The engine test kills aria2-next mid-download with `taskkill /F`, checks the
restart and the downloaded bytes, removal with file deletion, and history after
reopening. `python scripts\test-server.py` serves throttled files for trying
the app with many live downloads.

## Measure

With `OPENDM_UI_TIMING` set to a file path, the app appends one line per
batch of changed rows: `rows,total,apply`, the UI-thread milliseconds to
apply it, the total including the layout pass it causes. Frames longer than
20 ms append `-1,ms`.

Measured on Windows 11, 3840×2160 at 150%, Release build, 5,123 rows with 60
live downloads from `test-server.py`:

| Case | Median | p90 |
| --- | --- | --- |
| Live rows off-screen | 0.11 ms | 0.37 ms |
| 16 live rows on screen | 1.9 ms | 6.6 ms |
| Sorted by speed, live rows on top | 5.5 ms | 15 ms |

Changing the sort column costs one frame of 35-45 ms; changing the search
text, which resets the list, one of 70-90 ms. Scrolling 3 rows per frame,
95-97% of frames take under 20 ms.

Rechecked after the dialogs, Settings and the tray's status line were added
(the tray counts queued and paused rows on every update): 60 live rows per
update, median 0.77 ms and p95 0.96 ms on the UI thread with 5,001 rows.

What made the list fast, in case it regresses:

- Rows draw progress with a scaled rectangle. A `ProgressBar` re-runs its
  template on every value change, about 1 ms per visible row per tick.
- The `ItemsStackPanel` cache is one viewport. Off-screen realized rows keep
  live bindings and redraw on every tick.
- `DownloadList` never sends Move: the ListView treats it like a Reset,
  re-binding every row and clearing the selection.
- Live sorts compare speed as displayed, break ties by the current order,
  and sort precomputed keys.

## Layout

| File | Role |
| --- | --- |
| `Program.cs` | Entry point; single instance through `AppInstance` |
| `App.xaml.cs` | Creates the core, window and tray icon; quits cleanly |
| `DownloadStore.cs` | Applies the core's changed rows on the UI thread |
| `DownloadItem.cs` | Row view model; raises a change per field |
| `DownloadList.cs` | The visible collection; small reorders become moves |
| `MainWindow.xaml(.cs)` | Title bar, sidebar, toolbar, list, dialogs, keys |
| `TrayIcon.cs` | Notification-area icon (H.NotifyIcon) and its menu |
| `ToolWindows.cs` | Sizing, placing and Enter/Esc for the small windows below |
| `DownloadInfoWindow.xaml(.cs)` | Download File Info, and `NewDownloads`, where every new download goes |
| `BatchDownloadWindow.xaml(.cs)` | The several-files list |
| `ProgressWindow.xaml(.cs)` | One download's progress, details and completion |
| `SettingsWindow.xaml(.cs)` | Settings pages; Open at sign-in through the Run key |
| `SiteLogins.cs`, `LoginWindow.xaml(.cs)` | Site logins in Credential Manager, and Login Required |
| `AddressWindow.xaml(.cs)` | Refresh download address |
| `Format.cs`, `Native.cs` | Formatting, links, Win32 helpers |

## List styles (to port from macOS)

The macOS app lets the user pick one of three list designs; the choice is
remembered and List is the default. The Windows app currently has only the
Columns table. Add the other two as alternative item templates on the same
virtualized list, switched by a three-way toggle in the toolbar and
Ctrl+1 / Ctrl+2 / Ctrl+3, saved in local settings:

| Style | Row height | Contents |
| --- | --- | --- |
| Cards | 104 | Card with a 10 px corner radius, inset 10 px from the sides and 4 px top and bottom, 1 px separator border. 36 px file icon; semibold name; status line in the status color with its symbol, plus speed and time left while downloading (failed rows show the error); full-width 5 px bar; "40% · 82 MB / 209 MB". A pill of Pause/Resume/Retry/Open, Show in folder, Copy address and Remove buttons at the top right. Selection is an accent outline. |
| List | 54 | 32 px icon; name; a 4 px bar only while unfinished; detail line such as "82 MB of 209.7 MB · 258 KB/s · 8 min left", in red with the error for failed rows. Two fixed button slots at the trailing edge: pause/resume/retry, and show in folder (finished rows, or on hover). |
| Columns | 26 | The existing table. Status shows a colored symbol and a short word ("Failed", with the error as a tooltip); progress, speed and time left only while they mean something. |

Status colors: downloading uses the accent color, paused orange, completed
green, failed red, queued a tertiary gray. The macOS sources are
`apple/Sources/OpenDM/RowCells.swift` (Cards and List) and `Cells.swift`
(Columns). Recheck the 5,000-row test in each style.

## Behavior checked on Windows 11

- Tray icon (H.NotifyIcon 2.4.1): tooltip with the total speed, menu with
  Show downloads, New download…, a status line ("No active downloads",
  "5001 paused", "2 downloading · 257 KB/s"), Resume all and Pause all (off
  when they would change nothing), Settings… and Exit; left click shows the
  window. Efficiency mode stays off on purpose (`ForceCreate(false)`); it
  would throttle downloads.
- Single instance: a second launch exits and shows the running window.
- Closing hides the window; Exit stops the engine within 2 s and leaves no
  `aria2-next.exe`. Killing the app also ends the engine
  (`--stop-with-process`).
- Killing `aria2-next.exe` shows "Restarting the download engine…", starts a
  new engine and the downloads continue.
- Space pauses or resumes the selected rows; the selection survives live
  updates and re-sorting.
- Light and dark mode, including switching while running.
- Header alignment at 150%, and at 100% with the app forced to 96 DPI
  (`__COMPAT_LAYER=DPIUNAWARE`).
- New Download, dropped links and browser downloads go through Download File
  Info (one link) or the several-files list, which follow the running
  download for its name and size; with confirmation off they start at once.
  Cancel removes the download and its file.
- A server that asks for a login (the test server's `/private/`, user
  `opendm`, password `secret`) gets the saved login once, then Login
  Required; Remember stores it in Credential Manager. aria2 reuses a login
  it has accepted for the rest of its session, for every download from that
  host.
- Settings saves half a second after a change; speeds are entered in KB/s
  and saved in bytes/s; Open at sign-in adds and removes the `OpenDM` Run
  value. Logins can be added and removed there.
- Refresh download address: waits, asks, and continues the old download
  from the new address; closing the question treats the download as new.
  The restart keeps the part done without gaps from the start of the file
  and downloads the rest again.

## Browser extension on Windows

- `opendm-host.exe` ships next to `OpenDM.exe`. At each launch the app writes
  `<data>\browser\org.opendm.host.json` (and a Firefox variant) and points
  `HKCU\Software\<browser>\NativeMessagingHosts\org.opendm.host` at them
  for Chrome, Edge, Chromium, Brave, Vivaldi and Mozilla.
- The app listens on `\\.\pipe\opendm-browser-<hash>`, the hash coming from
  the data folder. With OpenDM closed, the host starts it with `--background`
  and answers within a second. The app starts without the browser's pipe
  handles; with them, the first answer never reached the browser.
- The first hello installs `yt-dlp.exe` and `deno.exe` into `<data>\tools`,
  and a YouTube page's formats come back through them.
- `tests\browser\run.ps1` loads `extension/` unpacked in a throwaway Chrome
  profile and checks capture (cookie, referer and user agent reach the
  engine), Alt-click, the HLS quality menu and its MP4, the video button,
  Download all links and the proxy hand-off: 25 of 25 pass in Chrome and in
  Edge (`$env:CHROME` = msedge.exe). It quits a running OpenDM first, and
  leaves the native-host registry keys pointing at its temporary profile
  until OpenDM next starts. The Firefox test still runs on macOS only.
